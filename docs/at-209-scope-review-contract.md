# Authenticated project scope review draft (AT-209)

The public API [PR #39](https://github.com/oicrruf/estimate-api/pull/39), at commit `17d5ad5746e423844a885415d7ba804a321e00b7`, supplies the reviewed OpenAPI fixture in `tests/fixtures/at209-scope-review-openapi.json` (SHA-256 `0f13af69dfac409072b66a3d75e940c9bc7ea9970ac5788c0fbf1cc1edd8bcf9`). This is a **draft** reference, separate from the app's currently approved canonical OpenAPI and API SHA. The ordinary `npm run contract:check` verifies the fixture and operation shape after its existing canonical tests; it does not advance the live pin.

`src/app/api/scope-review-preview.ts` describes `POST /v1/projects/{projectId}/scope-review-preview`. A caller must provide a typed authenticated project editor context, a 1–100 character idempotency key, an explicit API base URL, and an injected fetch transport. The client sends Bearer authorization and omits browser credentials. It validates a nonblank brief of at most 4,000 Unicode code points and requires the response to name the same project and explicitly remain pending, review-required, non-persisted, and not commercially ready. A 404 maps only to “not found”; it does not reveal whether a project is absent or membership was revoked. HTTP and network failures return bounded codes without exposing response bodies.

No app route imports this client, no default fetch transport exists, and no authenticated session or project editor permission is produced by this app. Unit tests use synthetic data and mocked fetch only. The earlier local composer candidate remains separate because it was based on an older visual branch and had a hard-coded project ID. These tests do not verify sign-in, a live API call, a hosted service, or project membership.

Before wiring a UI, integrate API PR #39, verify its actual `develop` SHA and OpenAPI bytes, then follow [contract synchronization](contract-sync.md) to update the canonical app copy and pin. A real auth adapter must supply the project editor context from a verified session, and UI work must keep the feature disabled without it. Review both status handling and idempotency with the integrated backend before enabling calls.
